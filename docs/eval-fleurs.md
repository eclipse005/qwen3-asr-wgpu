# FLEURS evaluation — all 29 available languages, both systems, both models

**What this measures.** WER/CER against human transcriptions (the thing that
matters), plus RTFx and per-clip alignment between our wgpu port and the Python
`-hf` reference.  Alignment (byte-identical output on the same clip) is the
regression signal: it catches porting bugs that a WER table would hide.

## What runs

| run | system | tag | model |
|---|---|---|---|
| `w06` | this port (wgpu tower + CPU decoder) | `w06` | `Qwen3-ASR-0.6B-hf` |
| `w17` | this port | `w17` | `Qwen3-ASR-1.7B-hf` |
| `py06` | Python `transformers` reference (fp16, cuda:0) | `py06` | `Qwen3-ASR-0.6B-hf` |
| `py17` | Python reference | `py17` | `Qwen3-ASR-1.7B-hf` |

* **Languages**: the 30 Qwen3-ASR supports; FLEURS covers 29 of them
  (`tools/fleurs_langs.tsv`).  Cantonese (`yue_hant_hk`) is missing from the
  reachable mirror, and the 22 Chinese dialects have no FLEURS coverage at all.
* **Clips**: 20 per language, **evenly spaced across the test set sorted by file
  size ≈ duration**, so short and long clips are both represented instead of
  whatever sits at the head of the tsv.  Both systems pick the same clips, from
  the file size — never a random draw.
* **Decode**: greedy, `max_new_tokens=256`, language auto-detected (not forced).
* **Timing**: both systems time the same span, "read the wav → text", with one
  GPU job at a time (the 8 GB card cannot hold two ASR clients).

```powershell
powershell -File tools/fetch_fleurs.ps1        # once: data -> eval_data/fleurs (git-ignored)
powershell -File tools/run_eval_all.ps1        # the four runs + the final table, serial
```

## Data source

`modelscope.cn/pengzhendong/fleurs` (huggingface.co and hf-mirror.com are not
reachable from this machine): `test.tsv` (columns: id, filename, raw,
normalized, …) plus `audio/test/<id>.wav`, 16 kHz mono PCM16.

## Scoring (`tools/score_asr.py`, `tools/score_sweep.py`, `tools/score_final.py`)

Both sides are normalized identically before scoring:

* `en` — whisper's `EnglishTextNormalizer` (numbers/ordinals/contractions), so
  `twentieth century` and `20th-century` compare equal.
* `zh` — `BasicTextNormalizer` + `cn2an` (Chinese numerals to digits).
* `ar`, `fa` — diacritics, tatweel and alef/ya/ta-marbuta folded to one form
  (21.3% → 16.4% on Arabic; the variant spellings were being scored as errors).
* everything else — `BasicTextNormalizer` (lowercase, symbols out, CJK-aware).
* `zh`/`ja` also drop Latin-script runs: FLEURS keeps the original Latin name in
  the reference (`…埃尔多安recep tayyip erdoğan通话…`) although the recording only
  carries the transliteration, so scoring it measures the dataset, not the model.
* Primary metric per language: CER for the scripts without word boundaries
  (zh/ja/ko/th), WER elsewhere.

Known interpretation caveats: Japanese orthographic variants (`子供`/`子ども`)
are *not* merged, so its CER is pessimistic; Chinese time expressions
(`十一点三十五`) are not converted by `cn2an`.

## Results

`docs/eval-fleurs-final.md` is generated by `tools/score_final.py` and holds one
row per language with all four WER/CER numbers, all four RTFx numbers and the
alignment percentages.

### The alignment noise floor (why it is not 100%)

Per-language alignment is quoted over 20 clips, so "80%" means four clips — and
the differences are tiny.  `tools/diff_systems.py` classifies every differing
clip (byte-identical / punctuation only / 1-2 units / 3+ units):

| | clips | byte-identical | differ (1-2 units) | 3+ units | cross-system distance |
|---|---|---|---|---|---|
| 0.6B | 580 | 557 (96.0%) | 19 | 2 | **0.219%** |
| 1.7B | 580 | 563 (97.1%) | 10 | 5 | **0.244%** |

Those differences sit **exactly on the clips where the model itself is unsure**:
on the clips where the two systems agree the WER against the human reference is
21.9% (0.6B) / 13.3% (1.7B) for both; on the clips where they differ it is
~39% / ~29.5% for both.  The shape of a difference is one word swapped for
another equally dubious word (`løne`/`lunne`, `Νανλάπ`/`Δανλάπτ`) with the rest of
the sentence identical afterwards — the signature of a **near-tie flip**, not a
porting bug: the two implementations do not share an arithmetic order (torch's
GEMM/SDPA kernels versus our WGSL kernels, f16 accumulation in the audio tower),
so a one-ulp difference at a near-tie picks the other token.  A bug would diverge
progressively and hit whole languages, not one word in four clips out of twenty.

Reproduce:

```text
python tools/diff_systems.py --ours w06 --other py06     # 0.6B
python tools/diff_systems.py --ours w17 --other py17     # 1.7B
```
